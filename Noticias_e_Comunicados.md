# Implementação da página "Notícias e Comunicados"

## Objetivo

Implementar a página **Notícias e Comunicados** do Portal de Parceiros
Catedral, buscando os dados diretamente da tabela existente
`public.wp_comunicados`.

Não criar nova tabela e não alterar a estrutura existente.

## Estrutura existente

``` sql
create table public.wp_comunicados (
  id bigint generated by default as identity not null,
  titulo text not null,
  conteudo text not null,
  imagem_url text null,
  destaque boolean not null default false,
  ativo boolean not null default true,
  data_publicacao timestamp with time zone not null default now(),
  data_expiracao timestamp with time zone null,
  created_by uuid null,
  created_at timestamp with time zone not null default now(),
  updated_at timestamp with time zone not null default now(),
  constraint wp_comunicados_pkey primary key (id),
  constraint wp_comunicados_created_by_fkey foreign key (created_by)
    references auth.users (id) on delete set null
);
```

## Regras de exibição

Exibir somente registros que atendam simultaneamente a:

1.  `ativo = true`;
2.  `data_publicacao <= agora`;
3.  `data_expiracao IS NULL` ou `data_expiracao > agora`.

Não apagar registros expirados nem alterar automaticamente `ativo`.

Ordenar primeiro por `destaque DESC` e depois por
`data_publicacao DESC`.

## Cabeçalho da página

**Título:** Notícias e Comunicados

**Subtítulo:** Acompanhe novidades, informações e comunicados
importantes do Programa de Parceiros Catedral.

Preservar o layout protegido, sidebar, tipografia, espaçamentos e padrão
visual já existentes no Portal.

## Cards

Cada comunicado deverá aparecer em um card contendo:

-   imagem, somente quando `imagem_url` estiver preenchido;
-   badge ou indicação visual discreta de **Destaque**, quando
    `destaque = true`;
-   título;
-   data da publicação;
-   conteúdo.

Não mostrar ao parceiro `id`, `created_by`, `created_at`, `updated_at`,
`ativo` ou `data_expiracao`.

A ausência de imagem não pode deixar um grande espaço vazio nem quebrar
o layout.

## Conteúdo

`conteudo` é `text`. Nesta primeira versão, renderizá-lo como texto,
preservando parágrafos e quebras de linha.

Não utilizar `dangerouslySetInnerHTML`.

## Datas

Apresentar `data_publicacao` em formato brasileiro, preferencialmente:

`28 de agosto de 2026`

Respeitar corretamente o timestamp com timezone e evitar deslocamentos
indevidos de data.

## Estado sem registros

Quando não houver comunicados válidos, mostrar:

**Nenhum comunicado no momento**

Quando houver novidades do Programa de Parceiros Catedral, elas
aparecerão aqui.

## Tratamento de erro

Se a consulta falhar, não mostrar mensagens técnicas do Supabase ao
parceiro.

Mostrar:

**Não foi possível carregar os comunicados neste momento. Tente
novamente mais tarde.**

O erro técnico pode ser registrado para diagnóstico conforme o padrão
existente no projeto.

## Supabase

Antes de implementar:

1.  localizar os clientes Supabase já existentes;
2.  verificar como as páginas protegidas atuais fazem consultas;
3.  reutilizar a arquitetura existente;
4.  respeitar autenticação e RLS.

Não utilizar `SUPABASE_SERVICE_ROLE_KEY` no navegador e não contornar
RLS.

Se o usuário autenticado não tiver permissão de `SELECT` em
`wp_comunicados`, apenas informar que a política RLS precisa ser
revisada. Não criar ou alterar políticas sem autorização.

## Rota e menu

Antes de criar arquivos, localizar a opção **Notícias e Comunicados** no
menu lateral e identificar sua rota atual.

Implementar na rota efetivamente utilizada pelo Portal. Não criar rota
duplicada ou uma terceira versão caso existam estruturas paralelas em
`/portal` e `/protected`.

A opção do menu deverá abrir a página e manter o mesmo comportamento
visual de item ativo das demais opções.

## Não implementar administração

Esta tarefa é somente para leitura pelos parceiros.

Não criar:

-   cadastro;
-   edição;
-   exclusão;
-   upload de imagem;
-   painel administrativo;
-   alteração de destaque;
-   alteração de datas.

A administração dos comunicados será implementada separadamente.

## Cuidados com Next.js

Seguir o padrão das páginas protegidas que já funcionam.

Não adicionar `export const dynamic = "force-dynamic"` sem necessidade,
não criar optional catch-all e não alterar `next.config.ts`,
autenticação ou layout protegido para esta funcionalidade.

## Validação final

Após implementar, confirmar:

1.  projeto compilando;
2.  consulta somente a `wp_comunicados`;
3.  apenas registros ativos são exibidos;
4.  publicações futuras não aparecem antecipadamente;
5.  comunicados expirados não aparecem;
6.  registros sem `data_expiracao` continuam disponíveis;
7.  destaques aparecem primeiro;
8.  registros são ordenados do mais recente para o mais antigo;
9.  cards sem imagem funcionam corretamente;
10. página responsiva em desktop e celular;
11. nenhuma outra funcionalidade foi alterada.

## Restrições

-   Utilizar somente `wp_comunicados`.
-   Não criar tabelas ou campos.
-   Não alterar schema.
-   Não alterar RLS sem autorização.
-   Não utilizar tabelas antigas que não comecem com `wp_`.
-   Não modificar `CLAUDE.md` ou `DATABASE_SCHEMA.md` nesta tarefa.
-   Não alterar funcionalidades fora do escopo.

## Resultado esperado

A página **Notícias e Comunicados** será o mural de informações do
Portal.

O parceiro deverá encontrar automaticamente somente comunicados que
estejam:

**ativos + já publicados + ainda não expirados.**

Os comunicados marcados como **Destaque** aparecem primeiro, seguidos
dos demais em ordem de publicação.
